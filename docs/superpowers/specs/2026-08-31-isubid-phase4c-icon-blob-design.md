# Phase 4-C: ユーザーアイコン BLOB

作成日: 2026-08-31
ブランチ: `phase-4c-icon-blob`

## 背景

当初設計文書(`docs/superpowers/specs/2026-07-08-isubid-design.md:83`)は、ユーザーアイコンを
次のように宣言している。

| ユーザーアイコン | `GET /users/:id/icon` | 画像をDBのBLOBに保存(**静的配信化ポイント**) |

同文書は「序盤: インデックス追加・N+1解消・**画像BLOB外出し**の王道」(`:88`)を序盤の
攻略線に挙げており、アイコンはこの問題の**王道 DB チューニング枠**の一角である。

現状:

- `users.icon LONGBLOB` は `webapp/sql/00_schema.sql:11` に**既に存在するが、
  エンドポイントもデータも無い**(完全に未使用)
- シード20人(id 1〜20)は `INSERT INTO users (id, name, password_hash)` で投入されており
  `icon` は NULL
- 4-D(SPA フロントエンド)の設計は `<img src="/api/users/:id/icon">` を前提にしており、
  ベンチの `ProcessHTML` が自動で辿ると書いてある(`2026-08-30-isubid-phase4d-spa-frontend-design.md:176,323`)

## スコープ

含む:

- ジェネレータによる決定論的な PNG アイコン生成と、SQL ダンプへの BLOB 埋め込み
- `GET /users/:id/icon` の実装(仕込み込み)
- スナップショットへのアイコン sha256 の追加
- Prepare と Load でのベンチ検証
- Load シナリオへのアイコン取得の組み込み

含まない:

- **アイコンの採点**(§4 で理由を述べる)
- `/api` プレフィックスへの移行(4-D)
- アイコンのアップロード API(出題範囲外。当初設計にも無い)
- 採用スケールの再決定(4-E)

## 1. データ生成

### 画像

**64×64 の PNG。** ユーザー id から背景色と幾何学模様を導き、`image/png` で符号化する。
Go の png エンコーダは同じ入力・同じ設定に対して決定論的なので、`initial-data` の
決定論性(同じ seed から同じ出力)は保たれる。

**1人ずつ異なる画像であることが要件。** 全員同じ画像だと「1枚だけ返して使い回す」改悪を
ベンチが検出できない。§3 の sha256 照合が意味を持つのは、画像が id ごとに異なるからである。

**実サイズは生成後に実測して記録する。** 64×64 の単色+模様の PNG は数百バイト〜1KB 程度に
収まる見込みだが、見込みを設計文書に書き込まず、実測値を `docs/phase4-notes.md` に残す。

### アイコンを持たないユーザー

**生成ユーザーの約1割を `icon NULL` にする。** 判定はデータセットのシード付き乱数で行い、
どのユーザーが NULL かをスナップショットに記録する。

理由は2つ。

1. 実サイトに即している(アイコン未設定のユーザーは普通にいる)
2. **「404 を 200 にする」改悪をベンチが検出できる。** 参加者がキャッシュ層や静的配信を
   入れたとき、NULL ユーザーの扱いを間違えるのはよくある事故であり、そこを検証で押さえる

**シード20人(id 1〜20)は全員 NULL のまま**にする。`webapp/sql/90_seed_phase1.sql` を
変更せず、既存の値ベースのテストを壊さない。

ベンチが走行中に `Register` する新規ユーザー(`bench/scenario.go:359,571`)も
アイコンを持たないので 404 になる。これも整合している。

### SQL ダンプへの埋め込み

16進リテラル(`0x89504E47...`)で埋め込む。`initial-data/sqlout.go` の
`INSERT INTO users (id, name, password_hash) VALUES ...` に `icon` 列を追加する。
NULL のユーザーは `NULL` を書く。

**バッチサイズを users だけ下げる。** `initial-data/sqlout.go` の
`rowsPerStatement = 1000` は1行が数十バイトの前提で置かれている。アイコンが入ると
1行あたり2KB超(1KB のバイナリが16進で2倍)になり、**1つの INSERT 文が約2MB**に膨らむ。
MySQL 8 の `max_allowed_packet` 既定値(64MB)は超えないが、余裕を持たせる意味も含めて
users 用の行数を別に持つ(100行なら1文あたり約200KB)。

他のテーブル(auctions / bids / notifications)の行数は変えない。

### 生成物サイズへの影響

現在のコミット済み生成物は 2.4MB。

| スケール | 生成ユーザー | アイコン持ち(約9割) | ダンプ増分(実測して埋める) |
|---|---|---|---|
| `small` | 500 | 約450 | 実測 |
| `medium` | 2000 | 約1800 | (未コミット) |
| `full` | 5000 | 約4500 | (未コミット) |

**コミットするのは `small` のみ**という 4-A の方針は変えない。

## 2. エンドポイントと仕込み

```
GET /users/:id/icon
```

| 条件 | 応答 |
|---|---|
| 該当ユーザーが存在し `icon` が非 NULL | **200** / `Content-Type: image/png` / PNG バイト列 |
| 該当ユーザーが存在し `icon` が NULL | **404** |
| 該当ユーザーが存在しない | **404** |
| `id` が非数値 / パース不能 | **400** |

実装:

```go
// 意図的に遅い実装: リクエストのたびに LONGBLOB を丸ごと DB から読む。
// 画像を配るのに毎回 MySQL へ往復しており、静的配信へ外出しするのが想定の攻略線。
var icon []byte
err := h.db.GetContext(r.Context(), &icon, "SELECT icon FROM users WHERE id = ?", id)
// sql.ErrNoRows(ユーザーなし)と icon IS NULL のどちらも 404 にする

// 意図的に遅い実装: Cache-Control / ETag / Last-Modified を一切付けない。
w.Header().Set("Content-Type", "image/png")
w.Write(icon)
```

### 仕込みの内訳

| # | 仕込み | 参加者の想定改善 |
|---|---|---|
| 1 | リクエストごとに LONGBLOB を DB から読む | **BLOB 外出し**: `/initialize` でファイルへ書き出し nginx に配信させる |
| 2 | `Cache-Control` / `ETag` / `Last-Modified` を付けない | ヘッダ追加、静的配信への移譲 |
| 3 | 一覧1ページ(20件)を開くと最大20回のアイコン要求が発生する | 上記いずれか |

**3 が効き方の本体である。** 1枚あたりの転送量は小さいが、一覧を1回開くたびに20回の
DB 往復が増える。当初設計が「静的配信化ポイント」と呼んでいるのはこの構造を指している。

## 3. ベンチ検証

### スナップショットの拡張

`SnapshotUser` を新設し、生成ユーザーの `id` / `name` / `icon_sha256` を持たせる
(`icon_sha256` が空文字ならアイコン無し)。500件 × 64文字 ≒ 32KB の増分。

sha256 を持つのは、**「全員に同じ画像を返す」改悪を検出するため**である。画像そのものを
スナップショットに入れる必要はない。

### Prepare(静穏期・厳密照合)

- アイコンを持つユーザーを数人サンプルし、取得したバイト列の sha256 がスナップショットと
  一致すること、`Content-Type` が `image/png` であること
- **アイコンを持たないユーザー**(生成ユーザーのうち NULL のもの、およびシードユーザー)で
  **404** が返ること
- **存在しないユーザー id** で **404** が返ること
- **非数値の id** で **400** が返ること

### Load(走行中)

watcher が一覧を取得したあと、**そのページに現れた出品者のアイコンを取得する**
(ブラウザと同じ振る舞い)。取得したバイト列の sha256 をスナップショットと照合する。

**ベンチはイテレーションごとに新しいクライアントを作る**(`bench/load.go` の各
`*Iteration` が `NewClient` を呼ぶ)。つまり毎回キャッシュが空の「新規訪問者」であり、
アイコンは必ず再取得される。これが §2 の仕込み3を持続的な負荷にしている。

sha256 が一致しない場合は critical。走行中でもアイコンの内容は変わらないので、
false-FAIL の余地は無い(オークションの一覧と違い、時間で変化しない)。

**シードユーザーが出品したオークションでは 404 が返る。** これは正常なので critical に
しない。逆に、アイコンを持つはずのユーザーで 404 が返ったら critical。

## 4. アイコンを採点しない理由

**`ScoreGETIcon` のような採点タグは作らない。** これは意図的な判断である。

このプロジェクトは同じ形の罠を2度踏んでいる。Phase 3 の `ScoreGETFeed`(取得ごとに
加点したため、効率的な実装ほど不利になった)と、4-D の設計で明文化した
「1ページロードにつき1点、アセット単位では絶対に数えない」である。

アイコンに加点すると、**重いアイコンを大量に配るほど点が入る**という逆向きの誘導になる。
参加者が最適化して1リクエストあたりを軽くしても、加点は「回数」に付くので、
最適化の報酬が正しく出ない。

正しい構造はこうである。

- **アイコンはコストであって報酬ではない。** watcher は一覧を取るたびにアイコンを取得する
- アイコンを速く返せるようになると、watcher の1周が速くなる
- その結果 `GET /auctions` と `GET /auctions/:id` の回数が増え、**そちらの加点が増える**

つまり「BLOB 外出し」の報酬は、既存の採点タグのスループット向上として現れる。これが
出題として正しいインセンティブである。

**liveness floor(4-E1)の対象にもしない。** 採点タグでないため floor の枠組みに乗らない。
アイコンが全滅した場合は Load の sha256 照合と Prepare の検証が critical で捕まえる。

## 7. やらないこと(と、その理由)

### キャッシュヘッダを報酬にする設計

`Cache-Control` を付けた参加者を直接加点する仕組みは作らない。ベンチが
イテレーションごとに新しいクライアントを作る以上、キャッシュヘッダは
ベンチから見ると効果を持たない(毎回コールドキャッシュの新規訪問者)。

**主たる攻略線は「BLOB 外出し」であって「キャッシュ」ではない。** nginx がファイルを
配るのは、Go が MySQL から LONGBLOB を読むより桁で速く、そこで十分な差が出る。
静的アセットのキャッシュの話は 4-D(`webapp/public/` の配信)で扱う。

### アイコンのアップロード API

当初設計文書にも無く、出題の攻略線を増やさない。初期データとして配るだけにする。
