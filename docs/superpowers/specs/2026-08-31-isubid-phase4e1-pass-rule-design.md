# Phase 4-E1: 合否判定の liveness floor と減点の実効化

作成日: 2026-08-31
ブランチ: `phase-4e1-pass-rule`

## 背景

Phase 4-A のサイジング実測で、ベンチマーカー本体の欠陥が露呈した(`docs/phase4-notes.md`
持ち越し2)。`full` スケールの60秒走行で、採点対象6本のうち4本が**成功0回**のまま
`RESULT: PASS` が出力された。

```
GET /auctions            : 0回 (0点)
GET /auctions/:id        : 0回 (0点)
POST /auctions/:id/bids  : 0回 (0点)
GET /auctions/:id/bids   : 0回 (0点)
...
RESULT: PASS
```

### 機構

`bench/main.go` の合否判定は次の1行である。

```go
pass := criticalCount == 0 && appCount <= errorLimit && total > 0
```

- `errorLimit`(`bench/score.go`、値 100)は割合ではなく**絶対件数**
- クライアントのタイムアウトは10秒(`bench/client.go`)
- `full` では `GetAuctions` が毎回10秒ブロックしてタイムアウトし、bidder/watcher プールは
  60秒で約6周しかできず、アプリエラーは約60件に収まって100件の上限を下回った

**しきい値が絶対件数であるため、インセンティブが逆転している。** 10秒でタイムアウトする
「遅い全滅」は60秒で高々数十件のエラーしか生まないが、即座に5xxを返す「速い失敗」は
同じ60秒で上限を軽く超える。**遅く失敗する実装のほうが、速く失敗する実装より安全に
`PASS` を通ってしまう。**

合否ルールには「採点対象のいずれかが1回でも成功すること」を要求する項目が無い。最も近い
検査である `len(list) == 0` → critical(`bench/load.go`)は `GetAuctions` が**成功して**
空配列を返したときにしか発火せず、タイムアウトした場合には発火しない。

### 現在の対処と、それが破綻する理由

4-A・4-B のゲート手順は次のように書かれている。

> **採点対象すべてが0回でないことを目視で明示的に確認すること。**
> `RESULT: PASS` を信用してはならない。

これは人間(あるいはサブエージェント)が毎回忘れずに実行することに依存している。
4-C 以降を自律的に進めるにあたり、**この依存は必ず破綻する**。4-D では採点対象が
さらに増えて目視の負荷が上がる。

### 第2の問題: 減点が実質的に機能していない

`errorPenalty = 1`(`bench/score.go`)。4-A 時点(raw 6177)ではエラー100件で
1.6% の減点だったが、4-B のページネーション導入で raw が 19086 まで上がった結果、
同じ100件が **0.5%** になった。減点は事実上の飾りになっている。

これは 4-B の Task 8 レビューが指摘した項目(`docs/phase4-notes.md` 軽微リスト)である。

## スコープ

含む:

- 採点対象エンドポイントごとの **liveness floor**
- `errorPenalty` の引き上げ
- 上記2つのゲート手順・文書への反映

含まない:

- **エラーのエンドポイント紐付け**(§5 で理由を述べる)
- 採用スケールの再決定(4-E 本体)
- 4-E の残り18件の持ち越し

## 1. liveness floor

### ルール

Load 走行後、採点対象の各エンドポイントについて、**そのエンドポイントを叩くワーカーが
1つ以上有効なら、成功回数が floor 以上であること**を要求する。1つでも下回れば
`RESULT: FAIL`。

成功回数は既に `result.Score.Breakdown()` に入っている(`step.AddScore(tag)` は成功時
にのみ呼ばれる)。**新しい計測は要らない。**

### floor の値

```
floor = max(1, 走行秒数 / 10)
```

既定の60秒走行なら **6**。

この値の根拠は 4-B の `small` 実測である。

| エンドポイント | 実測(60秒) |
|---|---|
| `GET /auctions/:id` | 3250回 |
| `GET /auctions` | 2078回 |
| `GET /auctions (検索)` | 1723回 |
| `POST /auctions/:id/bids` | 1137回 |
| `GET /auctions/:id/bids` | 1137回 |
| `GET /notifications` | 513回 |
| `POST /auctions` | **493回** ← 最小 |

floor 6 は最小値の 1/80 であり、誤検知(false-FAIL)の余地はほぼ無い。同時に
「0回」だけでなく「ほぼ死んでいる」状態も捕まえられる。走行時間に比例させることで、
デバッグ目的で `-duration 10s` のように短く走らせても壊れない。

### ワーカー有効性による条件付け

`bench` は `-bidders` / `-watchers` / `-notifiers` / `-sellers` でワーカー数を指定できる。
デバッグ目的で一部を 0 にした走行で誤って FAIL しないよう、**そのエンドポイントを叩く
ワーカーが1つも無い場合は floor を課さない**。

| 採点タグ | 要求するワーカー |
|---|---|
| `ScoreGETList` | `bidders > 0 \|\| watchers > 0` |
| `ScoreGETSearch` | `watchers > 0` |
| `ScoreGETDetail` | `bidders > 0 \|\| watchers > 0` |
| `ScorePOSTBid` | `bidders > 0` |
| `ScoreGETFeed` | `bidders > 0` |
| `ScoreGETNotifications` | `notifiers > 0` |
| `ScorePOSTAuction` | `sellers > 0` |

この対応は `bench/load.go` の各 `*Iteration` が呼ぶエンドポイントから導いたものである。

### 出力

floor を下回ったエンドポイントは、判定の前に名指しで出力する。

```
LIVENESS: FAIL (floor 6回)
  GET /auctions            : 0回
  POST /auctions/:id/bids  : 0回
```

通過した場合は1行にまとめる。

```
LIVENESS: PASS (floor 6回、採点7本すべて到達)
```

**ゲート3の目視確認をこの行が置き換える。** ゲート手順から「目視で確認」を削除し、
`LIVENESS: PASS` の確認に差し替える。

## 2. errorPenalty の引き上げ

```
errorPenalty: 1 → 20
```

成功1リクエストあたりの平均得点は 4-B の実測で約 1.85点(19086点 / 10331回)なので、
**エラー1件 = 成功約11リクエストぶんの損失**になる。上限の100件で 2000点、raw 19086 に
対して約 10.5% の減点。

| エラー件数 | 減点 | raw 19086 に対する割合 |
|---|---|---|
| 10件 | 200点 | 1.0% |
| 50件 | 1000点 | 5.2% |
| 100件 | 2000点 | 10.5%(ここで `errorLimit` により FAIL) |

定数を選んだのは、参加者から見て振る舞いが読めるためである。raw に比例させる案
(0.5%/件)も検討したが、自己参照的で「スコアを上げるほどエラー1件の代償も大きくなる」
という直感に反する挙動になるため採らない。

**採用スケールを変えると相対重みはまた変わる。** 4-E で採用スケールを再決定する際に
再調整すること。

| `bench/main_test.go`(新規) | floor 判定の単体テスト |
| `docs/phase4-notes.md` | ゲート3の手順から「目視で確認」を削除し `LIVENESS: PASS` へ差し替え。持ち越し2 を「4-E1 で対応済み」と明記 |

`webapp/go` と `initial-data` は変更しない。

## 4. 完了ゲート

| ゲート | 内容 |
|---|---|
| G1 | 正しいアプリで60秒走行 → `LIVENESS: PASS`、`RESULT: PASS` |
| G2 | **`GET /auctions` を必ず失敗させる改変**(ハンドラ冒頭で 500 を返す)を入れると、`LIVENESS: FAIL` で該当エンドポイントが名指しされ `RESULT: FAIL` になること |
| G3 | `-sellers 0` で走らせても `POST /auctions` について FAIL しないこと(条件付けが効いている) |
| G4 | `-duration 10s` で走らせても floor が 1 になり FAIL しないこと |
| G5 | Prepare(`-prepare-only`)の挙動が変わっていないこと |

G2 は 4-A で見逃された欠陥そのものの再現であり、**このフェーズの存在理由**である。

## 5. やらないこと(と、その理由)

### エラー率ベースの上限

`errorLimit` を絶対件数から割合へ変える案を検討したが、**採らない。**

エラーは現在エンドポイント単位に紐付いていない(`result.Errors.All()` は文字列を含む
フラットな配列)。したがって全体のエラー率では「一部のエンドポイントだけが遅く壊れて
いる」を捕まえられない。例えばあるエンドポイントが6回成功・60回失敗していても、
全体の試行回数が1万回あれば 0.6% にしかならず、どんな閾値にも引っかからない。

**意味のある割合判定にはエラーのエンドポイント紐付けが必要**で、それは
`addErr` の呼び出し箇所すべてにタグを配る変更になる。liveness floor が「全滅」を
確実に捕まえる以上、費用対効果が合わない。

`errorLimit = 100`(絶対件数)は現状維持とし、**エラーのエンドポイント紐付けと
割合ベースの上限を 4-E の持ち越しとして記録する。**

### 「ほぼ死んでいる」の閾値の精緻化

floor を実測の最小値(493回)に近づければ検出力は上がるが、スケールやワーカー数を
変えたときに false-FAIL する。**false-FAIL がこのプロジェクトで最悪の結果である**以上、
桁違いに安全側の 6 を採る。
