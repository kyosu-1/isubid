# ISUBID Phase 4-A — 初期データジェネレータ 設計ドキュメント

作成日: 2026-08-30
ステータス: 承認済み(論点1〜4の方針合意済み)
親ドキュメント: `docs/superpowers/specs/2026-07-08-isubid-design.md`
先行フェーズ: `docs/superpowers/specs/2026-08-29-isubid-phase3-pubsub-design.md`

## 位置づけ

Phase 4（仕上げ）は独立したサブシステムを6つ含むため、単一の spec には大きすぎる。以下に分解し、依存順に個別の spec → plan → 実装サイクルを回す。本ドキュメントはその最初の 4-A を扱う。

| # | サブプロジェクト | 前提 |
|---|---|---|
| **4-A** | **初期データジェネレータ（本ドキュメント）** | なし（土台） |
| 4-B | 一覧の一貫化＋検索 | 4-A |
| 4-C | アイコンBLOB | 4-A |
| 4-D | SPAフロントエンド | なし（並行可） |
| 4-E | 負荷の段階増加＋検出力再検証 | 4-A〜4-D |
| 4-F | ドキュメント一式（レギュレーション/マニュアル/writeup） | 全部 |

4-A が土台なのは、データ規模が変わると Prepare の期待値・スコアの水準・何がボトルネックになるかが全て変わるためである。後回しにすると、その上に積んだ検証を作り直すことになる。

## 前提

Phase 3 完了時点（`main` = 75dc6b5）。エンドポイントは10本、ベンチは Prepare / Load(60秒) / Validation の3フェーズが動き、初期実装に対して `RESULT: PASS` を実測済み。

初期データは Phase 1 の `webapp/sql/90_seed_phase1.sql` のまま（users 20 / auctions 12 / bids 8）。`initial-data/` ディレクトリは存在しない。

## スコープ

**含む**

- `initial-data/` の Go 製ジェネレータ（乱数シード固定、規模パラメータ化）
- 生成物: users / auctions（closed・live・upcoming）/ bids / notifications の SQL ダンプ
- 正解スナップショット JSON（Prepare の照合用）
- `webapp/sql/init.sh` と `POST /initialize` の刷新
- ベンチ Prepare の一覧レベル検証をスナップショット照合方式へ移行
- 段階的サイジングの実測と、採用規模の決定

**含まない**

- **アイコンPNGの生成**（4-C。エンドポイント `GET /users/:id/icon` と同時に扱う。4-A の時点で生成しても配信先が無く、サイジング実測に死荷重を乗せるだけになる）
- 検索 `?category=&q=`（4-B）
- 一覧のトランザクション一貫化（4-B）
- ベンチの入札者・出品者が使うユーザープールの拡大（4-E）
- 負荷の段階増加（4-E）

## 論点と決定

### 論点1: 生成物の形と配布

**決定: ジェネレータが SQL ダンプをファイル出力し、`webapp/sql/init.sh` が `mysql` クライアントで読み込む。`POST /initialize` は `init.sh` を実行する。**

親ドキュメントのリポジトリ構成が既に `webapp/sql/init.sh`（ベンチ前初期化、`POST /initialize` から呼ばれる）を想定している。テーブルごとに別ファイルへ分けることで、サイズが問題になったファイルだけを GitHub Releases へ逃がす選択肢を残す。

現行の `postInitialize` は SQL ファイルを Go で読み込み `multiStatements` で流している。30万行規模ではファイル全体が単一の文字列としてメモリに乗り、実行も遅い。`mysql` クライアントへのシェルアウトは ISUCON 本家の慣行でもあり、バルクロードが桁違いに速い。

**副作用として app コンテナに `mysql` クライアントが必要になる**（`webapp/go/Dockerfile` の変更）。これは受け入れる。競技者が `init.sh` を最適化できるようになるのも本家同様で問題ない。

不採用:

- **`/initialize` 実行時にジェネレータを走らせる** — 30秒制限を圧迫し、生成の再現性を毎回の実行環境に依存させる
- **Go でファイルを読み続ける（現行方式の維持）** — バルクロードが遅く、30秒制限に対する余裕が削られる

### 論点2: 時間軸の相対化

**決定: closed は絶対時刻のまま。live / upcoming のみ、initialize 時に単一の UPDATE で相対化する。**

closed 1万件は「過去に終わったオークション」なので、走行時刻との相対関係を持つ必要がない。書き換えるのは走行中に状態が変わりうる live / upcoming だけでよい。

ダンプ内では live / upcoming の `starts_at` / `ends_at` を固定エポック `2000-01-01 00:00:00` 起点の時刻として保持し、initialize が次の1文で変換する。

```sql
UPDATE auctions
SET starts_at = DATE_ADD(NOW(6), INTERVAL TIMESTAMPDIFF(SECOND, '2000-01-01 00:00:00', starts_at) SECOND),
    ends_at   = DATE_ADD(NOW(6), INTERVAL TIMESTAMPDIFF(SECOND, '2000-01-01 00:00:00', ends_at)   SECOND)
WHERE id > 12 AND status IN ('live','upcoming')
```

Phase 3 の `auctionEndOffsets`（id ごとのループで10件を UPDATE）は対象が10件だから成立していた実装であり、300件には使えない。本方式は300行の一括 UPDATE 1文で済み、30秒制限に影響しない。

**`WHERE id > 12` が必須である。** Phase 1 シード（id 1〜12）は既存の `applyRelativeSchedule` によって既に「現在時刻＋オフセット」の絶対時刻になっている。この行に上記の変換を当てると、`TIMESTAMPDIFF(SECOND, '2000-01-01', <2026年の時刻>)` が約8億3600万秒となり、`ends_at` が2052年へ飛ぶ。シードと生成データで時刻の与え方が二重になるのは避けられないため、境界を明示的に切る。

境界値 12 はシードの最大 auction id である。ジェネレータは必ず id 13 から採番し（論点4）、`init.sh` はシードを先に投入するため、この前提は投入順序によって保証される。実装では両側で共有する名前付き定数（`webapp/go` 側と `initial-data` 側それぞれ）として持ち、直値を散らさない。

**Phase 1 シードのオフセット表は変更しない。** シードのオフセット（`4:12, 2:20, 8:28, 6:36, 10:44, 1:3600, …`）はベンチの Prepare が厳密に照合しており、ここを変えると Phase 3 の検証が全て壊れる。

### 論点3: Prepare の期待値

**決定: ジェネレータが正解スナップショットを JSON で出力し、Prepare は全件ではなく決定的に選んだサンプルを照合する。**

親ドキュメントの「初期データの正解スナップショット（各オークションの現在価格など）を JSON で持ち、Prepare フェーズの照合に使う」がこれにあたる。

**全件照合はできない。** Phase 3 で「Prepare が最初のクローズ（初期化時刻 +12秒）を追い越すと false-FAIL する」ことを記録している（当時の実測は 0.6〜1.2秒）。1万件を1件ずつ `GET /auctions/:id` で照合すれば確実に追い越す。

照合対象は次の3つに絞る。

1. **一覧の1ページ目** — 件数、`ends_at ASC` 順、各行のフィールド値をスナップショットと突合
2. **決定的に選んだ代表オークション（数十件）** — スナップショットが `sample_auction_ids` として明示する。closed / live / upcoming と、入札数の多寡を跨いで選ぶ
3. **総件数** — スナップショットの `counts` と、一覧の件数・後述する健全性クエリの結果

不採用:

- **ベンチが同じ乱数シードで期待値を再計算する** — ジェネレータとベンチにロジックが二重化し、片方だけ変更した場合に検出できない

**スナップショットの配布**: `initial-data/snapshot.json` としてコミットし、ベンチは `-snapshot` フラグ（既定値 `../initial-data/snapshot.json`）で読む。

### 論点4: 既存シードとの関係

**決定: 生成データは既存シードを置き換えず、その後ろに continue する。id 1〜12 は Phase 1 シードのまま、生成データは id 13 から。**

これが最も効く決定である。理由は `webapp/go` のテスト27本が既存シードの具体値に依存しているため。auction 1 の入札列 1500/1200/1000、`seed_user_05` のログイン、auction 11 の落札者 12 / 落札額 12000 など、値ベースのアサーションが全体に散らばっている。

置き換えると、これらを1万件規模のデータに対する性質ベースのアサーションへ全面的に書き直す必要が生じ、テストの検出力も落ちる。前置きに残せば **webapp のテストスイートは無傷、Prepare の詳細検証（auction 1 / 11 / 12）も無傷**で、書き直しが必要なのは一覧レベルの検証だけになる。そこは 4-B の一覧一貫化でどのみち手を入れる箇所である。

不採用:

- **完全置き換え + テスト全面書き直し** — 上記のとおり検出力を落としながら大きな手戻りを生む
- **テスト用の小さいデータとベンチ用のフルデータを二重に持つ** — 「いまどちらのデータで動いているか」が恒常的な混乱源になる

## ジェネレータの設計

`initial-data/` に独立した Go モジュール（`bench/` と同じ構成）。

```
initial-data/
├── go.mod
├── main.go          # CLI: -scale, -seed, -out
├── generate.go      # 生成ロジック（純粋関数中心）
├── generate_test.go
├── snapshot.go      # スナップショットJSONの構築と書き出し
└── out/             # 生成物（.gitignore しない。コミットする）
    ├── 91_users.sql
    ├── 92_auctions.sql
    ├── 93_bids.sql
    ├── 94_notifications.sql
    └── snapshot.json
```

**決定性**: `math/rand` を固定シード（既定 `20260830`）で初期化した `*rand.Rand` を1つ作り、全生成で共有する。同じ `-scale` と `-seed` なら生成物はバイト単位で一致すること。これをテストで固定する。

**規模パラメータ**: 名前付きスケールを3段用意する。数値は上限の目安であり、採用値は後述の実測で決める。

| scale | users | closed | live | upcoming | bids |
|---|---|---|---|---|---|
| `small` | 500 | 1,000 | 50 | 25 | 30,000 |
| `medium` | 2,000 | 4,000 | 100 | 50 | 120,000 |
| `full` | 5,000 | 10,000 | 200 | 100 | 300,000 |

`full` が親ドキュメントの目標値である。

**出力形式**: マルチバリュー INSERT（1文あたり1,000行）。単行 INSERT を30万個並べると読み込みが桁違いに遅くなる。

## 生成データの内容

### users

- 名前 `gen_user_%05d`（`seed_user_NN` と衝突しない）
- パスワードは全員 `password`。**bcrypt ハッシュは事前計算した1つの定数を全ユーザーで共有する**。5,000回の bcrypt cost 12 は生成に数十分かかるうえ、ハッシュが違うことに検証上の意味がない
- `icon` は NULL（4-C で扱う）

### auctions

- `seller_id` は生成ユーザーから。**シードユーザー 1〜20 は出品者にしない**（`GET /stats/me` のシード期待値が壊れるため）
- **closed**: `ends_at` は過去（走行時刻に依存しない絶対時刻。数か月に分散）。`winner_id` / `winning_price` を設定
- **live**: 固定エポック起点で `ends_at` を分散。走行中に一部が閉じる
- **upcoming**: `starts_at` が未来
- **`ends_at` 順と id 順を非相関にすること。** Phase 3 で `initialAuctionOrder`（`4,2,8,6,10,1,3,5,7,9`）を非相関に配置し、一覧の `ORDER BY ends_at ASC` を `ORDER BY id ASC` に書き換える改変を検出できるようにした。生成 live オークションが id 順＝`ends_at` 順で並ぶと、この検出力が生成データの重みで薄まる

### bids

- closed / live オークションに分配（upcoming には入札しない）
- **各オークション内で、id 昇順に amount が厳密単調増加であること。** これはベンチの `ValidateBidsInvariant` / `ValidateFeedPage` が検証する不変条件であり（Phase 2b で追加、`FOR UPDATE` 除去の検出器）、生成データが違反すると Prepare とウォッチャーが即 critical を出す
- **同一オークションの連続する入札は user が異なること。** 現実的でもあり、通知ファンアウトの重みも生む
- closed オークションでは `winning_price` = そのオークションの最大 amount、`winner_id` = その入札者。ベンチの `reconcileClosedAuction` と同じ不変条件

### notifications

- 生成ユーザー宛のみ。**シードユーザー 1〜20 宛の通知は生成しない**
- 理由: ベンチの `validateNotifications` はシードユーザーの outbid 件数を下限比較する。生成分が乗っても下限比較なので false-FAIL はしないが、`GET /notifications` の応答が初手から巨大になり、通知確認シナリオのコストが実データではなく生成データに支配される
- 件数の目安: 落札者のいる closed オークション1件につき数件（`won` 1件 + `outbid` 数件）。`user_id` インデックス無しのフルスキャンに走査対象を与えるのが目的

## `init.sh` と `POST /initialize`

```sh
#!/bin/sh
set -eu
# 環境変数は webapp/go と同じものを使う
mysql ... < "$SQL_DIR/00_schema.sql"
mysql ... < "$SQL_DIR/90_seed_phase1.sql"

# 生成データは明示的なオプトイン。ISUBID_INITIAL_DATA_DIR が設定されているときだけ読む。
if [ -n "${ISUBID_INITIAL_DATA_DIR:-}" ]; then
  for f in 91_users.sql 92_auctions.sql 93_bids.sql 94_notifications.sql; do
    mysql ... < "$ISUBID_INITIAL_DATA_DIR/$f"
  done
fi
```

**生成データの読み込みは環境変数による明示的オプトインとする。** 当初「ファイルが存在すればスキップ」を想定していたが、生成物はリポジトリにコミットするため常に存在し、条件として機能しない。その状態では `webapp/go` のテストが `POST /initialize` 経由で生成データを読み込んでしまい、`len(list) == 10` のような既存の値ベースのアサーション（27本のテストが依存）が全滅する。

- 生成ダンプの置き場は `initial-data/out/`。`webapp/sql/` には置かない
- `dev/compose.yaml` が app サービスに `ISUBID_INITIAL_DATA_DIR` を設定する（ベンチ走行時は常に生成データあり）
- `go test` はこの変数を設定しないため、シードのみで従来どおり動く

`postInitialize` は `init.sh` を実行し、その後に既存の `applyRelativeSchedule`（シード id 1〜12 のオフセット適用）を行う。論点2 の生成データ向け一括 UPDATE は、生成データを読み込んだ場合のみ実行する。

## ベンチ側の変更

- `-snapshot` フラグを追加。**既定値は空文字（生成データ非搭載モード）** とし、渡されたときだけスナップショット照合を行う。アプリ側の `ISUBID_INITIAL_DATA_DIR` と対になる明示的オプトインで、両側の食い違いを設定ミスとして表面化させる
- 空のまま実行した場合は現行どおり Phase 1 シードのみを前提とした検証を行う。CI の縮小構成や `webapp/go` のテスト環境でもベンチが動く
- スナップショット照合モードでは、まず一覧の件数がスナップショットの live 件数と一致することを確認する。シードのみの環境（10件）に対して誤ってスナップショットを渡した場合、ここで明確なエラーになり、静かに誤判定へ倒れない
- **既定値を「生成データあり」に切り替えるかは 4-F（レギュレーション文書）で判断する。** 生成データが常態になった時点で既定を反転させるのが自然だが、4-A の時点で反転させると `go test` と現行のワークフローが壊れる
- `ValidateInitialAuctionList` を、固定表照合からスナップショット照合へ移行。`ends_at ASC` 順の検証と id 順との非相関検出はそのまま維持する
- `expectedInitialAuctions`（id 1〜10 の詳細期待値）と auction 11 / 12 の検証は**変更しない**

## 段階的サイジングの手順と受け入れ条件

`small` → `medium` → `full` の順に、各スケールで以下を実測し、**すべてを満たす最大のスケールを採用する**。実測値は `docs/phase4-notes.md` に記録する。

| # | ゲート | 閾値 | 根拠 |
|---|---|---|---|
| 1 | `POST /initialize` の所要時間 | 15秒未満 | レギュレーションの30秒制限に対し半分の余裕を残す |
| 2 | Prepare（`-prepare-only`）の所要時間 | 6秒未満 | Phase 3 で「6秒を超えたらオフセット表を見直す」と記録した閾値。最初のクローズが +12秒 |
| 3 | 60秒走行 | `RESULT: PASS` / critical 0件 | 基本 |
| 4 | **`FOR UPDATE` 除去で FAIL すること** | 3回中1回以上で検出 | 下記 |

**ゲート4が最重要である。** 単調増加検出器は「同一オークションへの同時入札」に依存する。生成データが live オークションを200件足すと、出品者シナリオが作る約260件と合わせて約460件になり、Phase 3 で既に記録した希薄化リスクがさらに進む。規模を上げるほどこの検出力が落ちるため、**採用規模は「検出器が生きている最大規模」で決まる**。Phase 3 の実測は既定フラグ・60秒走行で1回目に検出できていた。

ゲート4が全スケールで失敗する場合、それは 4-A の問題ではなく入札の集中度の問題であり、4-E（負荷調整）へエスカレーションする。その場合は本 spec の範囲では `small` を採用し、判断を 4-E に持ち越す。

## テスト戦略

- **ジェネレータのロジックはユニットテスト**。特に「オークション内で amount が厳密単調増加」「`winning_price` = max(amount)」「`ends_at` 順と id 順が非相関」の3つは、ベンチの検証と直結するため個別にテストする
- **決定性のテスト**: 同じ `-scale` / `-seed` で2回生成し、出力が一致すること
- **スナップショットと SQL の整合テスト**: スナップショットの `current_price` / `bid_count` が、生成した bids から導かれる値と一致すること（スナップショットが SQL と別ロジックで作られていないことの確認）
- `webapp/go` のテストは生成データ非搭載で従来どおり通ること
- **ベンチのベンチ**: 採用スケールで `FOR UPDATE` 除去による FAIL を実測し記録する（ゲート4と同一）

## 実装順序

1. **4-A-1 ジェネレータ本体** — `initial-data/` モジュール、生成ロジック、ユニットテスト。出力は `small` のみ
2. **4-A-2 スナップショットと読み込み経路** — `snapshot.json`、`init.sh`、`postInitialize` の刷新、Dockerfile への mysql クライアント追加
3. **4-A-3 ベンチのスナップショット照合** — `-snapshot` フラグ、`ValidateInitialAuctionList` の移行、非搭載環境でのフォールバック
4. **4-A-4 段階的サイジング** — `small` / `medium` / `full` の実測、ゲート4を含む判定、採用規模の決定と生成物のコミット、`docs/phase4-notes.md` への記録

## 未解決・後続への持ち越し

- **生成物のリポジトリサイズ**: `full` の bids ダンプは概算15MB前後。コミットするか GitHub Releases へ逃がすかは、4-A-4 の実測で実サイズを見てから決める。判断は本 spec の範囲内で行い、結果を記録する
- **ベンチのユーザープール拡大**: 生成した5,000ユーザーは「データの重み」としてのみ存在し、ベンチの入札者・出品者は Phase 3 の制約どおりシードユーザー 1〜20 のみを使い続ける。プール拡大は `validateNotifications` の `seed_user_%02d` 逆引きに手を入れる必要があり、4-E で扱う
- **一覧のフィールド間レース**: 生成データで live オークションが増えると `GET /auctions` の N+1 が重くなり、非トランザクショナルな `summarize` のレース窓も広がる。一覧レベルの不変条件検証は 4-B で一貫化とセットで行う
